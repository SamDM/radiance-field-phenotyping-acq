Sync check target

Point both cameras at this screen and capture. The screen is a white field with five QR codes; the measurement is the dark band the panel leaves behind as it scans, which crosses that white field once per refresh.

What the codes carry

The four corner codes each encode {"frame":N,"id":K} with K = 1 top-left, 2 top-right, 3 bottom-left, 4 bottom-right. All five are painted in the same animation frame and therefore carry the same N — so if a photograph shows different values at different corners, the scanout boundary passed between them during the exposure. That brackets the exposure to a known point in the panel's scan.

The centre code encodes {"t":<epoch ms>,"n":N,"id":5,"g":[...]}, tying the frame number to the host clock and carrying the layout in g: viewport width and height, panel width and height, device pixel ratio, the inset o from each viewport edge to a corner code's dark pattern, that pattern's side length k, the measured refresh rate, and the stage's own inset from the viewport edge — all in CSS pixels, all read straight off the page's own layout rather than assumed by whatever reads this back later.

That is what makes a photograph measurable. The corner codes give four anchors in image coordinates; g gives the same four in page coordinates, at [o,o], [vs-o-k,o], [o,vl-o-k] and [vs-o-k,vl-o-k] for ids 1 to 4. Every length in g is in the panel's own frame, short axis first and long axis second, so none of it changes meaning when the phone is turned. The long axis is the scan axis.

Panel size is reported separately from viewport size because the scanout covers the whole panel: unless the page is fullscreen, a band halfway down the viewport is not halfway through the scan.

The plaintext number beside each corner is the same N, for reading by eye without decoding.

Turning the phone

The panel scans along one fixed axis of its own glass, and turning the phone does not move it. The page is therefore turned back against the system rotation, so the layout lands on the glass identically either way: the strips keep running along the scan, and each code id keeps naming the same physical corner. Only the text is turned the other way again, so it stays readable — that is the one thing that should look different in landscape.

Which way to turn it back is taken from the reported orientation angle. If that is wrong on a device it costs nothing structural, since the strips lie along the scan either way; it only rotates the id-to-corner mapping through 180 degrees. The frame numbers settle it regardless: the pair showing the higher number was scanned first, so those two codes are at the scan origin.

Why the bands are slanted

There are two scans, not one. The panel emits row by row, and a rolling shutter camera samples row by row. A pixel goes dark where the camera's exposure window at that point misses the panel's emission there, and the locus of that condition is a line whose slope is set by the ratio of the two scan rates. So the bands align with neither the screen nor the sensor, and their angle changes when you rotate the phone relative to the camera.

This is why the band angle is informative: with the phone in landscape the slope is tPanel·a / tRow, which measures the camera's row period once you know how many image pixels the screen spans.

Reading a sync error

Band position also depends on mounting geometry, which differs between the two cameras and is unknown. Do not compare absolute band positions. Instead take many frames and track how the difference between the two cameras' band positions varies: the static geometric offset cancels, the phone's own drift is common to both, and what is left is the relative clock behaviour, at sub-refresh resolution.

Capture settings

Keep the exposure well under one refresh period — a millisecond or two. Any longer and the band smears across the field and the flicker strips average to flat grey.

Screen at full brightness. OLED panels dim by strobing, which lays a second, faster banding over the one you want.

The two flicker strips invert once per refresh. Use them as a validity check on the exposure, and read the difference in boundary height between the left and right strip to get the band tilt directly.

The strips stop themselves after three minutes and show diagonal stripes instead; tap to re-arm. Alternating a large area between black and white every refresh provokes image retention. The white field itself is harmless by comparison, but do not leave the page up for hours.

Notes

Check the info line before trusting a run. worst is the longest gap between animation frames in the last second — compare it to the period implied by the Hz reading; roughly double means a frame was dropped. long counts those cumulatively. A dropped frame breaks the assumption that consecutive frame numbers are one refresh apart, and it leaves no trace in the photograph, so a run with a rising long count should be thrown away rather than analysed.

Screen sleep. The info line shows screen on when the page holds a wake lock.

blocked means the browser has the API but refused the request. Tap the screen — the first attempt happens at load, before the page has any user interaction, and tapping retries it. If it stays blocked, battery saver is the usual cause.

unsupported means the API is not there at all, which is what a plain http URL gets you: the wake lock needs a secure context, and only https, localhost and file:// count — an http address on the LAN or over Tailscale does not. So loading this page from a served http URL is convenient but costs the wake lock, where opening the file from the phone's own storage keeps it. Either way, raising the display timeout in Android settings works regardless and does not depend on the page at all.

The displayed time lags the clock by roughly one frame plus panel latency. That is common to both cameras so it cancels between them, but it makes this a poor way to check a camera timestamp against the phone's own clock, which is not synchronized to the acquisition host anyway.

Tap anywhere to re-arm the strips and to go fullscreen. Leaving fullscreen is by the system back gesture, so re-arming mid-session never moves the target.
